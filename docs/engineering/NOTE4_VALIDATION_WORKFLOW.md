# Note4 持续开发、综合验证与发布

## 分支职责

- `fix/robustness-20261029` 是当前持续开发/汇总线；功能与修复按逻辑批次进入。
- `validation/note4` 是长期滚动的集成验证线，固件和 WQN 两仓使用同名分支及各自独立工作树。
- `release/note-baseline-prod` 只接收已经完成相应验收的明确提交；验证分支合入不自动授权发布。

首轮固件来源包括 Word `204f648`、R-08 `2bb5f4c` 和已有 release 传输更新 `4b48b50`。
云端来源包括 `17df118` 与聚合线 `62d80c6`；后者包含 60 秒音频、原生 web search 服务端开关
和工作树部署工具。其他独立产品分支不自动并入。实际父提交及整合修正应记入每轮来源清单。

## 新代码进入验证线

1. 确认开发工作树与待合入提交归属，完成构建和受影响自动回归；提交完整批次。
2. 在验证工作树合并明确的提交，不在另一会话的工作副本上解决冲突。
3. 复核自动合并的调用边界，特别是存储 owner、scope 就绪、后台结果归属及云端契约。
4. 对受影响行为补回归；每轮交付实机包前运行综合门禁和零 warning SDK 构建。
5. 将未完成 HIL 明确记为 pending。开发/验证 checkpoint 可提交；高风险验收和发布必须
   完成对应 HIL 及独立审查。验证发现的普通缺陷应同步回开发线；跨功能整合修正单独记录并安排回移。

当前分支名不代表全部代码已验收。新合并会使受影响的结论待重新验证；旧记录始终属于旧提交。
主机测试、SDK 构建、远端 CI、提供商实测、设备 HIL、云端部署和生产验收分开记录。

## 固定实机包

验证分支可以继续前进；已经交付的包、清单、ELF 和测试日志保持不变。每轮清单必须包含：

- 固件提交和源码树、所有合入来源、工作树是否 clean；云端对应提交。
- 实际写入应用镜像的版本、ESP-IDF 版本、构建 profile 与配置摘要。
- 应用镜像、ELF、bootloader、分区表及 OTA 元数据的 SHA-256 和写入布局。
- 自动验证范围、失败/跳过/未执行项；HIL 对象、设备与故障条件和日志。
- 包含的功能，以及仍未接通的入口。三项 Word 首页等验收要求必须核对当前源码和原生 UI 测试。

验证版采用独立的 `val-日期.批次` 内部版本，必须从镜像中读回校验；目录名不能替代版本。
例如 `val-20261107.1` 是验证候选，不是正式 `1107.1`。若修改内部版本或配置重新构建，
新的镜像需要新摘要和相应验证，不覆盖旧包。

固件 WSL 工作树使用其自己的 `build-wsl`；加载 ESP-IDF 5.5.x 后，显式选择 profile 和验证版本：

```sh
WQN_RELEASE_VERSION=val-20261107.1 idf.py -B build-wsl -DWQN_BUILD_PROFILE=ai-local build
python3 scripts/check_firmware_profile.py --config build-wsl/config/sdkconfig.json --profile ai-local
python3 scripts/run_robustness_gate.py --output-dir /tmp/note4-validation-results
```

实际工作应先准备可追溯且私有的 sdkconfig，不输出配置中的凭证。不从另一个 build 目录复制
应用镜像冒充当前源码构建；先核对 project path、版本、ELF 和每个包文件摘要。

## CI、实机和发布

`validation/note4` 的 push 触发相关 CI 检查；这项配置不代表本地已经执行远端 CI。
云端音频上限必须与固件一致，原生 web search 仍由服务端显式 opt-in，默认关闭。

刷机、部署、数据库迁移和真实用户数据维修需各自的明确授权。存储故障、重置和断电测试
使用已经备份的可恢复测试介质。串口监听遵循 no-reset 入口，日志绑定实际镜像身份。
发布只提升明确完成验收的候选；不把滚动验证分支的最新 HEAD 自动当作发布版本。
